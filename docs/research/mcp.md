# Model Context Protocol (MCP) and its ecosystem — viability as the integration surface for cross-user AI-session messaging

> Decision brief — research sweep of 2026-07-14. Every key fact cites a live source
> fetched that day; an independent verifier re-checked each one (verdicts below).

## TL;DR

MCP (current spec 2025-11-25) is the only protocol all our target clients speak, and its official Go SDK is production-grade, so it should be our integration surface — but only via plain tool calls. The push primitives look tempting and are a trap: sampling is formally deprecated (SEP-2577, Final) and essentially unsupported by real clients, elicitation asks the human rather than the model, and the next spec revision removes server-initiated requests entirely in favor of a stateless request/response pattern. True push into a session exists today only as Claude Code's proprietary "channels" extension (research preview), which we can layer on as an optional adapter; claude.ai and ChatGPT can only poll via tool calls within an active turn.

## What it is

MCP is an open JSON-RPC 2.0 protocol connecting LLM applications (clients/hosts) to external capability servers. Current revision: 2025-11-25 (previous: 2025-06-18), with formalized governance (SEP-932), working groups (SEP-1302), and an SDK tiering system (SEP-1730). Transports: stdio (client spawns server as subprocess) and Streamable HTTP (single endpoint, POST for client messages, optional GET-opened SSE stream on which servers MAY send unsolicited requests/notifications); the 2024-11-05 HTTP+SSE transport is deprecated. Servers expose tools, resources, and prompts; clients may expose sampling (server requests an LLM completion, approval-gated, server sees the result), elicitation (server requests input from the USER — form or URL mode), and roots. Authorization is OAuth 2.1: a protected MCP server is an OAuth resource server that MUST serve RFC 9728 Protected Resource Metadata; clients MUST send RFC 8707 resource indicators; client registration is via Client ID Metadata Documents (recommended) or Dynamic Client Registration (deprecated in the draft spec). Crucially, the draft next revision (version string 2026-07-28) rearchitects MCP as stateless: no initialize handshake or sessions, server-initiated requests (sampling/elicitation/roots) replaced by "Multi Round-Trip Requests" (server returns input_required, client retries), and the GET notification stream replaced by opt-in subscriptions/listen limited to list-change events.

## Maturity

Spec cadence roughly two revisions/year: 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25, next draft dated 2026-07-28 (not yet released as of 2026-07-14). Governance is formalized with a feature lifecycle/deprecation policy (12-month windows). SDKs: TypeScript (12.8k stars, stable v1.29.0 2026-03-30, v2.0.0-beta.4 2026-07-13), Python (23.6k stars, stable v1.28.0 2026-06-16, v2.0.0b1 2026-06-30) — both mid-v2 rewrite; Go SDK is officially "maintained in collaboration with Google", stable v1.6.1 (2026-05-22), v1.7.0-pre.2 (2026-07-09), pushed the day of this research, claims full spec coverage across 2024-11-05 through 2026-07-28. Official MCP Registry: still "in preview, breaking changes or data resets may occur", though its codebase ships steadily (v1.8.0, 2026-07-13); it hosts public-server metadata only (no private servers). A maturity red flag for feature planning: the official client feature-support matrix is dead — the docs repo hosting it was archived 2025-04-08, modelcontextprotocol.io/clients now redirects to the homepage, and SEP-1814 (a proposal for a caniuse-style replacement) is still open. Its last snapshot showed sampling supported by exactly one client (fast-agent).

## What adopting it buys us

Universal client reach with zero client-side installs beyond a config entry: Claude Code, claude.ai/Claude Desktop, ChatGPT, Codex, Cursor, and VS Code all connect to remote Streamable HTTP MCP servers, so one hosted server covers the whole mixed-tooling team — the exact first-user scenario. Verified per-client support: Claude Code consumes tools, prompts (slash commands), resources (@-mentions), roots, and elicitation (form + URL, with an auto-respond hook), plus list_changed notifications and OAuth to remote servers; claude.ai/Desktop connectors support tools, prompts, and resources over Streamable HTTP with OAuth/DCR; ChatGPT supports tools (Apps SDK/connectors, Streamable HTTP recommended, OAuth 2.1 with Client ID Metadata Documents). On top of that, Claude Code uniquely offers true push today via its experimental channels extension: a local stdio MCP server declaring the claude/channel capability emits notifications/claude/channel and the content is injected into the live session as a <channel> tag — Claude reacts without the user typing — including a reply-tool pattern and remote permission relay. That is precisely our product's delivery mechanism, pre-built on one client. The Go SDK being Google-co-maintained, spec-complete, and current de-risks keeping Go as the implementation language. The OAuth story, while heavy, gives us real per-user identity — which the spec itself requires for any server holding per-user state.

## What it costs us

The core cost: MCP cannot push a message into the model's context on claude.ai or ChatGPT, and is moving further from that ability. Sampling — the only primitive that hands the server a model completion — is deprecated by SEP-2577 (status Final): low adoption, "few clients support sampling" (last official matrix: one client; none of our three targets), and the SEP explicitly tells new implementations not to adopt it. Elicitation reaches the user, not the model, and claude.ai/ChatGPT don't document supporting it. Core notifications are plumbing (list_changed etc.), not content injection, and the draft 2026-07-28 revision deletes unsolicited server-initiated requests (MRTR pattern) and narrows the notification stream to opt-in list-change subscriptions — so any design leaning on server push through core MCP breaks within ~a year. Claude Code channels are proprietary, research-preview, allowlist-gated (custom channels need --dangerously-load-development-channels; Team/Enterprise orgs must enable channels by policy), and stdio-only, so our hosted server needs a local bridge process per user. A multi-user hosted server means implementing a full OAuth 2.1 resource server (RFC 9728 metadata, RFC 8707 audience validation, identity-bound state — the spec forbids keying user state on session IDs) while the registration mechanism churns (DCR deprecated mid-2026 in favor of CIMD). Finally, ChatGPT/claude.ai only invoke tools during an active user turn, so cross-session latency degrades to "next time the human prompts."

## Recommendation

Adopt MCP as the integration surface, but design for its least common denominator: client-initiated tool calls. v1 should be a hosted Streamable HTTP MCP server exposing tools like send_message / check_messages / wait_for_reply (a long-running tool call that blocks until a reply or timeout arrives is the best cross-client approximation of push — Claude Code's default tool timeout is ~28h and progress notifications keep it alive; verify equivalents per client), with OAuth 2.1 + RFC 9728 for per-colleague identity. Explicitly do NOT build on sampling (deprecated, unsupported by all three target clients) and do not treat elicitation or core notifications as a message-delivery path. Layer true push as per-client adapters, starting with a Claude Code channels bridge (local stdio process forwarding from our server; accept the research-preview caveats and dev-flag requirement, and track its graduation). Keep Go: the official Go SDK is stable, Google-co-maintained, spec-complete including the auth primitives we need. Architect the server statelessly from day one — the 2026-07-28 revision removes sessions and the initialize handshake, which actually fits a message-relay design well. Budget a re-check when that revision ships (~2 weeks out). Publish to the official Registry at launch for discoverability, but treat it as marketing, not infrastructure (still preview).

## Open questions

- Does claude.ai/Claude Desktop support elicitation? The building-connectors doc lists tools/prompts/resources as supported and sampling/subscriptions/'advanced capabilities' as unsupported, but never names elicitation either way — needs an empirical test with a real connector.
- Do claude.ai and ChatGPT keep a long-running tool call (our wait_for_reply blocking pattern) alive, and for how long? Claude.ai/Desktop documents a 300-second tool timeout, which may force short-poll loops there; ChatGPT's limit is undocumented.
- When exactly does the next spec revision ship and is 2026-07-28 the final version string? SEP-2577 said 'expected June 2026'; the go-sdk README targets 2026-07-28; the revision was unreleased as of 2026-07-14.
- Will Claude Code channels graduate from research preview, and will third-party channels get a non-'dangerous-flag' path onto the allowlist (today it is Anthropic-curated, with Team/Enterprise able to self-allowlist via org policy)?
- What is Codex's and Cursor's precise MCP client feature set today (elicitation? notifications?) — not verified against vendor docs in this pass; the archived official matrix predates both products' current versions.
- Does ChatGPT surface MCP prompts and non-embedded resources at all, or only tools? Apps SDK docs mention 'embedded resources' for UI rendering but are silent on the general resources/prompts primitives.
- How disruptive will the stateless 2026-07-28 revision be for the Go SDK API we'd build against (v1.7.0 is still in pre-release), and how long will clients keep negotiating 2025-11-25?
