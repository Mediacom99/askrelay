# ChatGPT session extension points today (official docs)

> Decision brief — research sweep of 2026-07-14. Every key fact cites a live source
> fetched that day; an independent verifier re-checked each one (verdicts below).

## TL;DR

ChatGPT today is strictly pull-only for external systems: every integration surface (custom MCP connectors/apps, Developer mode, Apps SDK apps, GPT Actions) is a tool the model invokes during a user turn — there is no webhook, notification, or server-initiated path that puts content in front of the model in a live conversation. The closest push-like mechanisms are an Apps SDK widget calling sendFollowUpMessage after it has already been rendered in that conversation, and scheduled Tasks that poll at most hourly with explicitly no webhook support. Full MCP with write actions is a Business/Enterprise/Edu beta (web only, per-conversation confirmations); Plus/Pro get read/fetch-only developer mode. So a colleague's ChatGPT can answer our system's questions only when that colleague (or an hourly task) asks it to check.

## What it is

The set of officially documented ways an external system can interact with a ChatGPT session (web/desktop/mobile) as of 2026-07-14: (1) apps/connectors — remote MCP servers surfaced through the new Plugin Directory (which replaced the App Directory on July 9, 2026); the non-developer path requires read-only search+fetch tools for chat and deep research; (2) Developer mode — full MCP client (tools only, read and write) for Pro/Plus/Business/Enterprise/Edu on web; write actions gated by per-conversation confirmations and, in beta, to Business/Enterprise/Edu workspaces with admin publishing; (3) Apps SDK (preview) — MCP servers plus iframe widgets; the widget bridge exposes tools/call, ui/update-model-context, and sendFollowUpMessage; apps are reviewed and distributed via the directory; (4) Custom GPT Actions — legacy OpenAPI/REST tool calls inside custom GPTs, still live, model-restricted; (5) scheduled Tasks — user-owned polling jobs, max once/hour, no webhooks; (6) Work with Apps on macOS — desktop-side context pull from IDEs/terminals when the user sends a message. ChatGPT's MCP support is tools-only: no sampling (open feature request), and no documented elicitation, resources, or server notifications.

## Maturity

Extremely fast-moving and mid-migration. Developer mode with full MCP arrived ~Sept 9-10, 2025 (still labeled beta and 'Elevated risk'); the app directory launched Dec 18, 2025 with third-party submissions; on July 9, 2026 — five days before this brief — OpenAI replaced the App Directory with a Plugin Directory, launched the ChatGPT Work agent, retired group chats and Atlas, and shipped a new desktop app merging Chat, Work, and Codex. Help-center articles were updated 4-5 days ago and still contain inconsistencies (e.g., the developer-mode guide says Plus is eligible while the help FAQ only addresses Pro read/fetch). Apps SDK is 'preview'; monetization is 'details in the future'; Business-plan apps cannot even be updated after publishing ('at launch'). GPT Actions persist without a deprecation notice but are visibly legacy (restricted to GPT-4o/4.1 since June 16, 2025). Adoption evidence for apps is real (directory with named partners, submissions open), but the surface renames roughly every six months (connectors → apps → plugins), so anything we build against it needs an abstraction layer and a maintenance budget.

## What adopting it buys us

Targeting ChatGPT via a remote MCP server is viable for the pull half of our product and reuses the exact artifact we'd build for Claude: one MCP server can serve ChatGPT chat, deep research (read-only), developer mode, company knowledge, and the API. Concretely, colleague B on Business/Enterprise can enable our server as a workspace app (admin-published) and both read pending questions and post answers (write tools, confirmed per conversation); B on Plus/Pro can at least read the inbox via developer mode. Deep research can consume our data read-only. An Apps SDK widget gives a real UX upgrade: after B invokes our app once in a conversation, the widget can render the incoming question and, on B's click, call sendFollowUpMessage or tools/call to send the reply — approximating an interactive inbox inside the chat. Scheduled Tasks give a crude keep-alive: an hourly task ('check my AI inbox and summarize new questions') that notifies B. Enterprise admin tooling (RBAC, per-action allowlists, parameter constraints, Compliance API logging) actually fits our small-team-at-a-company scenario well — IT can scope exactly what our tool may do.

## What it costs us

The core cost is architectural: no push, period. ChatGPT never sees our content unless the user (or an hourly task) triggers a turn that calls our tools — so 'A's session sends a question directly into B's live ChatGPT' is impossible today; we must ship an out-of-band notifier (Slack/email/OS notification) telling B to ask ChatGPT to check the inbox, which reintroduces human latency. Plan gating fragments the experience: write-capable MCP is a Business/Enterprise/Edu beta requiring admin enablement and publishing; Plus/Pro developer mode is read/fetch-only per the help center; mobile is excluded entirely ('web only'); agent mode ignores custom apps. Write actions trigger confirmation cards per conversation (resetting on refresh), adding friction to every answer B sends. We inherit OpenAI's churn: three naming regimes in seven months, Business apps not updatable after publish, frozen tool snapshots that error when our server evolves until an admin manually refreshes. MCP sampling/elicitation/notifications are unsupported, so no server-initiated model calls or structured user prompts. Directory distribution requires OpenAI review; private workspace publishing avoids that but limits us to admin-managed installs.

## Recommendation

Design the product around pull-with-notification, not push — for ChatGPT this is not a choice. Ship one remote MCP server (streamable HTTP + SSE, OAuth, tools annotated with readOnlyHint) exposing an inbox pattern: check_messages (read), reply (write), plus search/fetch aliases so the same server works in ChatGPT chat, deep research, and non-developer connector mode. Target Business/Enterprise workspaces as the primary ChatGPT persona (full write MCP, admin-published app); treat Plus/Pro as read-only degraded mode and mobile as unsupported. Pair it with an out-of-band nudge (Slack/webhook to B: 'your ChatGPT has a question waiting — open chat and say check inbox') and optionally document an hourly scheduled task as a poor-man's poller. Defer an Apps SDK widget to v2 — nice UX, but preview-stage and review-gated. Do not build on GPT Actions (legacy, model-restricted) or expect sampling/elicitation/webhooks to appear on any committed timeline. Critically: this asymmetry (Claude-side agents can poll aggressively; ChatGPT-side humans must initiate) should be a first-class product concept — message durability and 'answer whenever B's session wakes up' semantics, not real-time delivery.

## Open questions

- Whether Plus-plan developer mode permits write tools today: the official guide lists Plus as eligible for developer mode (full MCP client), but the help article's beta note gates write/modify to Business/Enterprise/Edu and its FAQ only addresses Pro (read/fetch) — Plus write behavior is unconfirmed from official sources.
- Whether ChatGPT supports MCP elicitation or server notifications (e.g., tools/list_changed): no official page states support or non-support; only sampling has an explicit (community-visible) gap via the open GitHub feature request.
- What 'repeat on a schedule or trigger' means for ChatGPT Work scheduled tasks (July 9, 2026 release note) — whether any event-based trigger exists that could reduce polling latency, given the Tasks article simultaneously says webhooks are not supported.
- Whether sendFollowUpMessage requires a user gesture inside the widget or can fire autonomously (e.g., on a timer while the widget is mounted) — the reference documents no restriction, but observed behavior is unverified and the host bridge changed recently per community reports.
- How the July 9, 2026 Plugin Directory migration affects custom-app plan gating and the app-review pipeline going forward — the docs were updated days ago and Business 'cannot update after publishing' is flagged 'at launch', so current limits may shift within weeks.
- Whether custom connectors for Plus/Pro remain unavailable in the EEA/Switzerland/UK (stated in a 2025 release note; current regional status not restated in the refreshed articles) — matters if any colleague is EU-based.
- Whether the new (July 9, 2026) unified desktop app supports custom MCP apps/developer mode, given the help FAQ's 'web only' answer predates it and plugins are said to be available 'on web and desktop'.

## Independent verification

Recommendation and TLDR are safe to act on; treat the maturity section's specifics as directional, not factual.
