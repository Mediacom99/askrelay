# Commercialization research — Willingness to pay in agent/AI-dev infrastructure (2026): does askrelay's category have demonstrated WTP, and at what price shape?

> Input to the commercialization-posture decision (D-13/D-08 review), researched
> 2026-07-19 against live sources; every evidence item independently re-checked.

## TL;DR

Adjacent categories show real but modest WTP in three shapes: per-seat ($29–100/user/mo for daily-use tools like LangSmith and HumanLayer's new IDE), per-instance/bundle ($9–99/mo for hosted MCP infra on Glama/Smithery), and usage ($29–229/mo tiers at Composio). Nobody has demonstrated WTP for cross-person or inter-agent messaging specifically: the only company squarely in that lane (BAND, $17M seed, April 2026) has no published pricing and no named paying customers, and HumanLayer — the closest analog to "approval-gated agent actions as a product" — pivoted away from its approval API to a $100/user/mo coding-agent IDE. The evidence supports keeping Apache-2.0 with a paid-tier-ready hosted design, not switching to open-core-now or proprietary; and Apache-2.0's permissiveness means a paid hosted tier never locks out, while relicensing the core does lock progressively at first external DCO contribution.

## Assessment

Honest verdict: askrelay's specific category — cross-person, approval-gated AI-session messaging — has zero documented willingness to pay anywhere. The one direct competitor (BAND) is pre-pricing and enterprise-only; the closest behavioral analog (HumanLayer's approval API) was abandoned by its own maker in favor of a per-seat coding IDE, which is a strong signal that approval-gating is a feature, not a purchasable product. What the market does pay for, at verified price points: (1) seat-shaped tools people open daily — $39/seat (LangSmith) to $100/seat (HumanLayer IDE); (2) hosted-infrastructure convenience — $9–99/mo per instance/bundle (Glama, Smithery, Langfuse Core/Pro), with Smithery's free-hosting shutdown proving free hosted infra bleeds money; (3) usage-metered integration calls — $29–229/mo (Composio). VC money ($6M AgentMail, $17M BAND, $29M Composio) is flowing into adjacent categories on thesis, not revenue — that is conviction about the future, not evidence of present WTP. The realistic price shape for askrelay, if a paid hosted tier ever materializes, is the Langfuse/Glama pattern: free self-host forever, hosted team tier around $5–15/user/mo or a flat ~$50–100/mo per relay/team — small numbers, viable only as solo-maintainer side revenue, not a company. Nothing found contradicts the maintainer's prior; everything found argues against betting the license on unproven revenue.

## Implications for askrelay

Keep D-13 (Apache-2.0 everything, DCO, no CLA) and reject open-core-now and proprietary: there is no demonstrated WTP to monetize, and the trust requirement of a consent/security product plus the flagship-OSS goal are worth more than optionality on revenue that no one in the category has captured. Critically, the TIMING question resolves favorably: because inbound contributions are Apache-2.0 (permissive), a paid hosted tier, proprietary hosted add-ons, or an open-core split where NEW closed components sit alongside the Apache core remain possible forever — no external contribution ever blocks selling services or building proprietary code on top of Apache-2.0 code. What locks at the first external DCO contribution is only the ability to relicense EXISTING contributed code to something more restrictive (AGPL relay fallback, or closing the core) without rewriting that contributor's code or obtaining consent — so the documented AGPL-relay fallback direction narrows with every merged outside PR, while the paid-hosted direction never does. Practical moves: (1) build the hosted-hardening work package paid-tier-ready as planned (multi-tenancy seams, quota hooks, billing-neutral config); (2) per Smithery's lesson, cap the free hosted instance aggressively (rate limits, message TTLs, small quotas) and state from day one that a paid tier may exist later — Langfuse proves this coexists with permissive OSS; (3) accelerate D-17 trademark only if a paid tier launches, since Apache-2.0 lets anyone else host it commercially and the mark is the only moat.

- ❌ **FAILED** — Legal-mechanics claim (tldr + implications): 'relicensing the core does lock progressively at first external DCO contribution' — i.e., the AGPL-relay fallback (or closing the core) becomes impossible for EXISTING contributed code without rewriting that contributor's code or obtaining consent, and 'narrows with every merged outside PR'.

The brief's claim is a common piece of open-source folklore (conflating 'you cannot revoke the Apache-2.0 grant on released code' — true — with 'you cannot distribute derivatives of contributed code under other terms' — false).
  - **Correction:** Apache-2.0 imposes no such lock. Section 2 grants every downstream recipient (including the maintainer) a 'perpetual, worldwide, non-exclusive, no-charge, royalty-free, irrevocable copyright license to reproduce, prepare Derivative Works of, publicly display, publicly perform, sublicense, and distribute the Work' from each contributor; Section 4 expressly permits providing 'additional or different license terms and conditions... for any such Derivative Works as a whole,' provided the Apache-2.0 conditions are met (include the license, mark modified files, retain notices/NOTICE). The FSF confirms Apache-2.0 is one-way compatible with GPLv3 (and hence AGPLv3). So after external DCO'd contributions, the maintainer can still ship future versions of the whole tree under AGPL — or even proprietary — without contributor consent or rewrites; the only thing that is irrevocable is that already-released code stays available under Apache-2.0 to everyone (which is equally true with zero external contributors). The brief's open_questions item hedges toward this ('sublicensing mechanics... worth one hour of counsel'), but the tldr and implications assert the lock as settled fact and it should not enter the decision log that way. Note this error is conservative — the true position gives askrelay MORE optionality than claimed, so it does not undermine the keep-Apache-2.0 recommendation.
  - Evidence: <https://www.apache.org/licenses/LICENSE-2.0>
