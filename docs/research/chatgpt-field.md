# ChatGPT extension points — practitioner field reports (custom connectors / remote MCP, Developer Mode, Apps SDK, GPT Actions, Tasks)

> Decision brief — research sweep of 2026-07-14. Every key fact cites a live source
> fetched that day; an independent verifier re-checked each one (verdicts below).

## TL;DR

Practitioners confirm ChatGPT can attach custom remote MCP servers via Developer Mode (Pro/Plus/Business/Enterprise/Edu, web only), but the field record is one of repeated silent regressions, tools that stop being callable mid-conversation, a 60-second hard tool-call timeout, and a doc-contradicting rule that a custom connector locks the conversation away from built-in apps. Nobody was found who made a ChatGPT session answer another AI session through a connector; the bridges that exist use AppleScript UI automation or screen-watching, because ChatGPT is outbound-client-only with no inbound push. GPT Actions are visibly decaying with each model rollout and should be avoided. For our product, ChatGPT is a workable but flaky asker (outbound MCP client) and a poor unattended answerer.

## What it is

This brief covers what people who actually shipped against ChatGPT's extension points report, as opposed to what the docs claim. The extension points: (1) Developer Mode custom MCP connectors — ChatGPT as a remote MCP client over SSE/streamable HTTP with optional OAuth, tools-only, read tools free-running and write tools gated by per-conversation approval prompts; (2) Apps SDK — MCP servers plus iframe widgets, submitted to an app directory with a multi-round human review; (3) legacy GPT Actions in custom GPTs (OpenAPI-based); (4) scheduled Tasks, which per one vendor blog can invoke connectors on a timer. The practitioner corpus is rich: the OpenAI community forum has dozens of active bug threads on connectors (regressions, invocation failures, truncation), a 517-point HN thread from the Sept 2025 Developer Mode launch, engineering blogs (Render field guide, dev.to), and OpenAI's own '15 lessons building ChatGPT apps' (Feb 4, 2026) which tacitly admits invocation reliability must be engineered via naming, annotations, and value lists. Crucially, all extension points are outbound: ChatGPT calls your server; nothing lets an external system push a message into a live ChatGPT session.

## Maturity

Developer Mode launched Sept 9, 2025 (beta framing; the current official guide no longer carries a beta label and lists Pro/Plus/Business/Enterprise/Edu, web only). Field maturity is low-to-medium: an Oct 2-8, 2025 regression silently detached all custom connectors from the model; June 2026 brought unannounced response-truncation changes; June-July 2026 threads show tools becoming uncallable under context pressure with no official fix. Apps SDK: announced Oct 2025, submissions open, but two acknowledged critical widget bugs (Mar 24, 2026) survived two announced fixes and were still reproduced May 27, 2026; a June 10, 2026 practitioner post describes multi-round review with resubmissions. Connectors still don't work inside Projects (staff-confirmed gap, no timeline, Dec 2025-Feb 2026). Workspace sharing was admin-only until fixed Sept 9, 2025; now requires org publish plus per-user auth. GPT Actions are in visible decay: GPT-5.5/5.6 rollouts (June-July 2026) broke action dispatch intermittently with zero requests reaching servers, unacknowledged. Pattern across all of it: OpenAI ships model/platform changes that break integrations without changelogs, and forum threads, not release notes, are the de facto status page.

## What adopting it buys us

Supporting ChatGPT as a client of our system is genuinely feasible and is the only way to reach ChatGPT users: a teammate on Plus or above enables Developer Mode on the web, an admin publishes our remote MCP server to the workspace once (post-Sept-2025 sharing works), and their ChatGPT session can then call tools like ask_colleague or fetch_answers against our relay. Because Apps SDK, Developer Mode, and (per OpenAI's docs) the whole apps platform are MCP-based, one remote MCP server covers ChatGPT, claude.ai, Claude Code, Cursor, and Codex — practitioners confirm the same server attaches across these clients. Write-action approval prompts are actually a feature for us: B's human approving an outgoing answer maps onto ChatGPT's native confirm-before-write flow, and correctly annotating read tools (readOnlyHint) keeps the ask/poll side friction-free. The vendor-reported Tasks capability (hourly polling of a connector) offers a crude unattended inbox-check pattern if it verifies. Practitioner lessons (short tool descriptions under the 5,000-token cap, structuredContent-only responses, sub-60s calls with async job IDs and polling) are all documented in field reports, so we can design around known failure modes rather than discover them ourselves.

## What it costs us

The ChatGPT leg will be our least reliable client and needs defensive design plus support burden. Hard constraints: 60s tool-call ceiling (staff-confirmed) forces an async ask-then-poll protocol — no blocking wait for a colleague's answer; no inbound push, so a ChatGPT session cannot be woken when a question arrives (polling only, hourly at best via unverified Tasks); web-only Developer Mode excludes mobile; connectors don't work in Projects; and activating our connector locks the conversation out of built-in apps (intentional per OpenAI, June 2026) — a real UX cost for users who also use Notion/Calendar apps. Reliability tax: documented silent regressions (Oct 2025 detachment, June 2026 truncation), tools dropping out of the callable set as conversations grow, and invocation that must be prompt-engineered. MCP surface is tools-only — no sampling, elicitation, or server-initiated notifications — so our protocol can't rely on richer MCP features if we want ChatGPT parity. Plan gating (paid plans only, workspace admin publish for Business) adds onboarding friction for a small team. GPT Actions and desktop-automation bridges are dead ends: Actions break with each model rollout, and the existing ChatGPT-Claude bridges (AppleScript, screen-watching) are fragile macOS hacks we should not emulate.

## Recommendation

Support ChatGPT as a second-class, outbound-only client of our relay via one remote MCP server in Developer Mode — do not architect the product around ChatGPT's capabilities. Concretely: design the wire protocol async-first (send_question returns an ID immediately; check_inbox/get_answer are separate read-only tools), keep every tool call well under 60 seconds, annotate reads with readOnlyHint, return structuredContent without a duplicate JSON text block, and keep tool descriptions terse. Treat ChatGPT as an asker and a human-triggered answerer (user opens ChatGPT, says 'check my agent inbox and answer pending questions', approves writes via the native confirmation prompt); do not promise unattended ChatGPT responses in v1 — the only unattended path (Tasks + connectors) rests on a single vendor blog and needs a spike to verify. Reject GPT Actions (decaying with every model rollout) and the Apps SDK for v1 (directory review friction and unresolved widget bugs buy us nothing for a developer tool; revisit if we later want a polished inbox UI inside ChatGPT). Budget explicitly for breakage: the field record shows unannounced regressions roughly quarterly, so our docs should include a ChatGPT-troubleshooting page and our server should log whether ChatGPT ever calls tools after connecting. The lock-out of built-in apps and Projects incompatibility must be stated in onboarding docs, not discovered by users.

## Key facts

   - Source: <https://developers.openai.com/api/docs/guides/developer-mode>

   - Source: <https://community.openai.com/t/how-to-configure-long-mcp-tool-call-times-for-chatgpt-app/1379834>

## Open questions

- Do scheduled Tasks really invoke custom Developer Mode connectors unattended, and what happens to write-approval prompts in an unattended run? Only a vendor blog (PortEden) claims it; the official help-center article returned HTTP 403 and could not be cross-checked — needs a hands-on spike on a paid plan.
- Does ChatGPT's MCP client support elicitation, sampling, or server-initiated notifications in any form? The official guide describes tools only and community threads never mention them working, but absence of mention is not a tested negative.
- At what context size do connector tools drop out of the callable set? The June 2026 'connected but not invokable' failure mode is community-diagnosed (context pressure), never confirmed or quantified by OpenAI.
- Does the July 2026 GPT-5.6 rollout that broke GPT Actions dispatch also degrade MCP connector invocation, or are the two dispatch paths independent?
- Will the 'conversation restricted to developer MCPs' lock-out lift? OpenAI hinted it may change 'as ChatGPT and Codex merge' (June 25, 2026) — worth re-checking before launch since it shapes our onboarding warnings.
- Exact current Business/Enterprise admin-publish flow and whether Plus-plan teammates in a personal (non-workspace) context can each add the connector independently — the sharing thread predates the apps rename and the help-center page was unfetchable.
- Whether ChatGPT's connector invocation reliability differs materially between chatgpt.com and Codex (OpenAI itself recommended Codex as the workaround for the apps-coexistence restriction) — could make Codex the better-supported OpenAI-side client for our tool.
