# Security prior art: prompt injection and data leakage in inter-agent messaging

> Decision brief — research sweep of 2026-07-14. Every key fact cites a live source
> fetched that day; an independent verifier re-checked each one (verdicts below).

## TL;DR

Cross-person agent messaging is a textbook "lethal trifecta" system: colleague B's model gets private data access, untrusted content (text authored by A's model, itself possibly injected upstream), and an exfiltration channel (its reply back to A, plus any tools it can call). Every major 2025-2026 incident (GitHub MCP, Supabase MCP, Asana MCP, EchoLeak/CVE-2025-32711, AgentFlayer zero-click ChatGPT connectors) is a concrete instance of this pattern, and vendors and OWASP now treat indirect prompt injection as unsolved at the model layer. For v1, table stakes are architectural: human approval gates on B's side, least-privilege/no-tool default for received messages, egress/allowlist controls, treating every inbound message as untrusted data (spotlighting-style framing), and signed sender identity. Fancier data-flow control (CaMeL) is deferrable R&D.

## Maturity

The threat literature is current and fast-moving. Willison coined the lethal trifecta on 2025-06-16 and documented the Supabase MCP case 2025-07-06. OWASP LLM Top 10 2025 (released 2025-03-12) ranks Prompt Injection #1 and Excessive Agency #6; OWASP has since shipped a dedicated Top 10 for Agentic Applications 2026 (Dec 2025) and a Practical Guide for Secure MCP Server Development (Feb 2026) plus a "Securely Using Third-Party MCP Servers" cheat sheet (Nov 2025). The MCP Security Best Practices doc is versioned to spec revision 2025-06-18. Incidents are confirmed and dated: EchoLeak (CVE-2025-32711, CVSS 9.3, disclosed June 2025, Microsoft-patched); Asana MCP cross-org exposure (~1,000 customers, June 5-17 2025); AgentFlayer zero-click ChatGPT connector exfiltration (Black Hat USA, Aug 2025). CaMeL is research (arXiv 2503.18813, Mar-Jun 2025) with released code but limited production adoption. Vendors publicly concede prompt injection may never be fully solved.

## What adopting it buys us

Adopting these patterns as design constraints (rather than bolt-ons) buys credibility and safety for an open-source tool whose entire premise is piping model-authored text between people. Concretely: a human approval gate on the receiving side neutralizes the "act autonomously on injected instructions" failure mode that caused every listed incident; least-privilege defaults (received messages cannot trigger tools/tool-calls without explicit scoping) breaks the trifecta's third leg; egress allowlists and disabling auto-rendering of remote images/links close the exfiltration channels used in EchoLeak and AgentFlayer; signed sender identity lets B's agent and B's human distinguish "A's session actually sent this" from a spoof or replayed payload. Treating inbound text as data-to-be-quarantined (spotlighting/delimiting) reduces, though does not eliminate, injection success. Together these turn "we built a prompt-injection delivery network" into "we built a messaging layer with defensible, documented security posture" — directly reusable for the project's threat-model doc.

## What it costs us

Cost is mostly UX friction and scope discipline, not licensing. Human approval gates add latency and clicks — the core value prop is "no human copy-paste," and approval-on-receive reintroduces a human in the loop, so you must design gates that are lightweight (e.g., approve-per-conversation, not per-message) and honest that unattended auto-reply is the dangerous mode. Least-privilege defaults mean the received message cannot silently call tools, which limits the "B's session answers by querying B's private repo" magic unless B explicitly grants it. Egress controls conflict with letting agents fetch/render arbitrary content. Signed identity needs a key model. Spotlighting is probabilistic (Microsoft's own data shows reduced-but-nonzero attack success) so it cannot be relied on alone. And no combination is a guarantee: vendors state injection may never be fully solved, so the product must surface residual risk honestly rather than promise safety — a documentation and expectation-setting cost.

## Recommendation

Treat the lethal trifecta as a hard design constraint, not a caveat. For v1, make these table stakes: (1) received messages are untrusted data by default and cannot trigger any tool call, file access, or outbound action without explicit per-scope human grant on B's side; (2) a human approval gate before B's session acts on or auto-replies to inbound content — ship "manual approve" as default, "auto-reply" as an explicitly dangerous opt-in; (3) egress controls — no auto-fetch/auto-render of remote images or links in messages (this alone kills the EchoLeak/AgentFlayer exfil channel); (4) signed, authenticated sender identity so origin is verifiable; (5) spotlighting-style framing that clearly demarcates inbound peer text as data. Defer: full CaMeL-style data-flow control (research-grade, integration-heavy), content-scanning "guardrail" classifiers (Willison: unreliable, false confidence), and cross-org tenant-isolation machinery (relevant only if you add a hosted multi-tenant relay). Write the threat model to state plainly that prompt injection is not solved and that auto-reply mode inherits the sending model's compromise. Go is fine; none of this hinges on language choice.

1. **The 'lethal trifecta' = private-data access + exposure to untrusted content + ability to externally communicate; combining all three enables exfiltration and there is no reliable model-level fix, so the advice is to avoid combining them.**

2. **GitHub MCP server could be hijacked via a malicious public GitHub issue to exfiltrate private-repo data; Invariant Labs (May 26 2025) says it is architectural and unfixable by server patches, mitigated only by least-privilege tokens and one-repo-per-session.**
   - Source: <https://invariantlabs.ai/blog/mcp-github-vulnerability>

   - Source: <https://simonwillison.net/2025/Jul/6/supabase-mcp-lethal-trifecta/>
   - Verified: Fetched via search; General Analysis + Willison describe the service_role over-privilege, hidden-instruction ticket, and read-only mitigation.

## Open questions

- Auto-reply mode is the core value prop but is exactly the unattended-agent configuration that made every listed incident possible — can a lightweight, per-conversation (not per-message) approval gate preserve enough of the 'no copy-paste' magic while keeping a human in the loop, or does safety force manual approval in v1?
- If B's session answers by querying B's private data/tools, B's agent has all three trifecta legs by design. Is the product willing to ship with received-message tool-calls disabled by default and require explicit per-scope grants, accepting reduced capability?
- Does a message authored by A's model, which may itself have been prompt-injected upstream, mean we must treat even authenticated, signed senders as untrusted content? (Signature proves origin, not benign intent.)
- What signed-identity/key model fits an open-source, possibly serverless P2P design without a central CA — and how do we prevent replay of a previously-signed malicious message?
- Which egress channels must be closed by default: remote image rendering, link auto-fetch, outbound tool HTTP? EchoLeak and AgentFlayer both used remote-image URLs — is disabling auto-render acceptable UX?
- Do we need OWASP's confused-deputy / tenant-isolation controls at all? Only if a hosted multi-tenant relay is introduced; a pure P2P design may sidestep the Asana-class bug — confirm during architecture.
- Is any content-scanning/classifier guardrail worth shipping given Willison's and vendors' position that they give false confidence, or should v1 rely solely on architectural controls plus honest disclosure?

## Independent verification

**Overall:** This brief is highly reliable on its core narrative and sources: 10 of 12 key_facts are fully confirmed against primary sources (Willison's lethal-trifecta and Supabase posts, Invariant Labs, Trail of Bits, Zenity, the MCP 2025-06-18 security best practices spec, both arXiv papers, Anthropic's support article, and OpenAI's Lockdown Mode — the last verified down to the 'limiting outbound requests' detail). The two failures are date errors, not fabrications: the OWASP LLM Top 10 2025 was released November 18, 2024, not 2025-03-12 (the brief appears to have picked up a translation-release date from the OWASP page), and the Asana claim presents June 5-17, 2025 — actually the patch/offline window — as the exposure period, when exposure ran from the May 1 launch to the June 4 discovery. Neither error changes the brief's conclusions. The more consequential weakness is in the prose: the tldr and benefits sections force the Asana incident into the lethal-trifecta/prompt-injection frame when it was a conventional tenant-isolation bug that approval gates would not have stopped, and the claim that disabling image auto-render 'kills the EchoLeak exfil channel' is true but unsupported by the brief's own EchoLeak sourcing. The recommendations themselves (untrusted-by-default inbound messages, approval gates, egress controls, signed identity, honest residual-risk disclosure) rest on confirmed facts and align with the verified vendor and OWASP positions; they can be adopted with confidence after correcting the two dates and softening the 'every listed incident' generalization.
