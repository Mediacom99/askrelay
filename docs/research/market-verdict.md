# askrelay — market verdict (go / no-go synthesis)

> Produced 2026-07-16 from six adversarially-verified market briefs
> (`market-*.md` in this directory) and a three-lens judge panel.
> The verdict is a recommendation; the maintainer decides.

## Verdict: **GO_WITH_CHANGES**

**Build it — thin, fast, and honestly framed: the demand case is unproven (and one shipped competitor already flopped), but the window is verified open, the falsification test is uniquely cheap, the downside is capped, and the failure mode converts into the best-evidenced adjacency.**

## Rationale

The panel split 2-1 (bull GO_WITH_CHANGES 72%, base-rate GO_WITH_CHANGES 70%, bear NO_GO 60%), but the verdict is not a vote count — it comes from weighing three considerations that dominate the rest.

DOMINANT CONSIDERATION 1 — the bear's best evidence is strong but convertible. The two sharpest bear points are (a) the askmesh natural experiment: the exact hypothesis (teammate-to-teammate agent Q&A over MCP, daemon mode) shipped 62 npm releases since March 2026 and got ~815 downloads; and (b) the quadrant mismatch: askrelay's moat (cross-vendor + cross-org + self-hosted + approval-as-product) surrounds the quadrant with the least demand evidence, while the quadrant with the only live user (Kosmoy, all-Claude-Code, same org) is exactly where vendor compression is plausible in 6-18 months. Both points are correct and both survive verification. But neither is dispositive: askmesh's failure is uninterpreted (no evidence of any distribution effort was found — the demand brief's exhaustive sweep turned up no launch anywhere), and the quadrant mismatch is a positioning and sequencing problem, not a build/no-build problem. Both convert into mandatory changes and kill criteria rather than a NO_GO — the bear's own flip-to-GO conditions (askmesh autopsy showing execution failure, real Kosmoy pair usage, co-maintainer + funded hours) are precisely what a cheap v1 plus two weeks of homework would produce.

DOMINANT CONSIDERATION 2 — the option value of a cheap, fast falsification loop. Almost no zero-expressed-demand project gets to test its hypothesis this cheaply: a deliberately thin build (single Go binary + SQLite, design fully decided and adversarially verified), a captive daily-use first customer, and a binary metric (do distinct human pairs exchange approval-gated messages weekly without prompting?) answerable within weeks of deployment. A NO_GO now throws away information that costs perhaps two months of evening work to acquire, while the vendor-clock brief verifies the corner is empty today and structurally unserved for 24+ months on the cross-vendor/cross-org axes. When the test is cheap, the window is open, and the downside is quiet invisibility rather than reputational damage, decision quality favors a scoped bet with pre-registered kill criteria over abstention.

DOMINANT CONSIDERATION 3 — modal-outcome economics. The base-rate judge's frame is the right one: plan for the median world (dozens of stars, Kosmoy as only heavy user, a security probe within months, the month-6-12 abandonment cliff) and require that world to pay. It does: a working internal tool for the employer, a published threat model and verified-research decision log demonstrating design rigor, and an approval-gateway core (gates, revocable grants, signed envelopes, durable inbox) that carries over nearly intact to the one adjacency with real commercial signal (HumanLayer, gotoHuman, Cloudflare HITL primitives) — the layer no vendor is incentivized to make vendor-neutral. The salvage value is unusually high for this reference class.

WHY NOT UNQUALIFIED GO: expressed demand is genuinely zero; the only public test of the hypothesis returned near-zero adoption; solo-maintainer base rates are brutal and 'one contributor = dead by default' is now an explicit ecosystem heuristic; and the security-positioned nature inverts the usual cost-benefit — askrelay pays the full hardening cost up front, gets no demand credit for it, and a slow vulnerability response would be uniquely on-brand-damaging for a consent product. These do not kill the bet, but they dictate its shape: thin scope, fast ship, repositioned pitch, same-owner wedge included, askmesh autopsy first, kill criteria written into the implementation plan before code, and an incident-ready (not merely design-ready) security posture.

VERIFIER CORRECTIONS BINDING ON PLANNING: Claude Code WAU is ~1-2M (not 2-4M); mcp_agent_mail tripled then decelerated (not flat); askmesh is a shipped competitor (not a squatter page); Anthropic has already shipped first-party link-based session sharing with team members — the vendor-risk picture must include it.

## Scenarios

### Bull case

v1 relay deploys at Kosmoy within ~10 weeks; multiple human pairs exchange approval-gated messages weekly without prompting, validating the core loop in the most favorable cohort. The same-owner cross-machine scenario (documented day one) captures the only demand pool with verified pull (the #28300 cluster, mcp_agent_mail's audience), and a well-executed launch (Show HN + MCP directories + the unclaimed 'Your AI can ask my AI' framing) lands in the hundreds of stars. One or two external teams deploy unsolicited — ideally a cross-org pair (OSS co-maintainers or contractor/client), the first organic signal in the moat-protected quadrant. A security researcher probes within 90 days; fast, non-dismissive response becomes a trust asset consistent with the product's consent pitch. A co-maintainer joins, flipping the dead-by-default signal; Kosmoy funds maintenance hours. By mid-2027 askrelay is the reference implementation for cross-person, approval-gated session messaging, the 'approvable' abstraction has opened the HITL/approval-gateway adjacency, and vendors' same-org moves validate rather than compress the category. Probability: roughly 10-15%.

### Base case (most probable 12-month trajectory)

v1 ships in Q4 2026 after a compressed docs phase. Kosmoy usage is real but lumpy — some weeks pairs exchange messages, some weeks Slack wins; the tool proves genuinely useful for a subset of question types (B's live local context: uncommitted code, private repos) and irrelevant for the rest. Launch yields dozens to low hundreds of stars; the same-owner scenario draws most of the interest; cross-person external adoption stays near zero. mcp_agent_mail-style deceleration sets in by month 4-6. At least one security report arrives and is handled competently. The maintainer hits the month-6-12 cliff with Kosmoy as the only heavy user and faces the pre-registered checkpoint honestly: either the approval-gateway pivot (extending 'approvable' from messages to actions, riding the HumanLayer/Cloudflare HITL current) or a deliberate wind-down to maintained-internal-tool status. Either way the project pays as designed: a working tool at the employer, a portfolio flagship demonstrating verified research, threat modeling, and disciplined execution, and a reusable approval/inbox core. Probability: roughly 60-65%.

### Bear case

The docs phase drags past September; v1 slips into late Q4. Kosmoy colleagues try it for a novelty week, then revert to Slack — the 'colleagues just message each other' reading wins in the most favorable possible cohort, leaving no cheaper test to run. Meanwhile Anthropic org-scopes agent-teams messaging or extends first-party session sharing (the 6-18 month 'plausible' converting to real), compressing the only segment with a live user before external validation exists. The launch lands sub-50 stars into an ecosystem that discounts solo maintainers by default; the askmesh autopsy, done late or not at all, turns out to have contained the answer the whole time (demand absence, not execution failure). Worst variant: a consent-bypass vulnerability lands while momentum is already gone, and a slow or defensive response — the one controllable reputational landmine — damages the maintainer's name in exactly the dimension (security rigor) the flagship was meant to showcase. Residual value: design documents and a lesson. Probability: roughly 25-30%; the reputational-damage sub-variant is largely behavioral and avoidable.

## Is this the right first flagship OSS project?

Yes, conditionally — this is a good FIRST flagship for this maintainer, with one honest reframe and one personal-capacity check. It is a good fit because the modal outcome still builds the flagship: the project's distinctive assets (adversarially verified research briefs, a recorded decision log, a published threat model, approval-as-the-product architecture) demonstrate exactly the design rigor a flagship is supposed to signal, independent of star count; the captive daily-dogfooding first user directly attacks the number-one killer in the reference class (maintainer abandonment, not scandal); the pitch is novel and product-shaped, which is what separates the tail winners from the 52%-dead median in this window; and the downside of a quiet first flagship is invisibility, which is reputationally cheap. The required reframe: success must be defined, in writing, as 'shipped a rigorous, secure, working tool with a real user and handled scrutiny well' — if the maintainer privately needs 500 stars or external adoption to feel this succeeded, this is the wrong project, because zero expressed demand plus category creation makes that outcome a low-probability tail. The capacity check: a security-positioned project carries an indefinite solo incident-response obligation on top of a day job; the evidence says fast, non-dismissive vulnerability response is the single controllable variable separating trust-preserving projects from reputation-damaging ones, and for a consent product a slow patch is uniquely on-brand-damaging. If the maintainer can commit to that SLA and to at least a monthly release cadence for six months, this is the right flagship; if not, scope v1 smaller until both commitments are credible, or choose a project without the security bullseye.

## Kill criteria (stop/pivot signals)

- PRE-CODE (by ~2026-08-01): the askmesh autopsy shows a competent, discoverable, actually-distributed product that teammates simply declined to use - i.e., demand absence rather than execution failure, with no credible variable askrelay changes. Stop before writing application code.
- SHIP DATE (2026-10-15): v1 relay not deployed and in use at Kosmoy by this date. The scope was too fat for the window and the maintainer's real capacity - cut v1 drastically or stop; do not extend the docs phase instead.
- CORE DEMAND CHECKPOINT (8 weeks post-deployment, hard stop 2027-01-31): fewer than 3 distinct human pairs at Kosmoy exchanging cross-person, approval-gated messages in at least 2 of any 4 consecutive weeks WITHOUT maintainer prompting. The most favorable cohort said no; execute the approval-gateway pivot or wind down to internal tool + portfolio artifact. Measure from relay metrics, not impressions.
- EXTERNAL VALIDATION (6 months post-launch, ~2027-04): zero unsolicited external deployments AND zero organic cross-org/cross-vendor demand signals (issues, forum posts, inbound contacts not solicited by the maintainer or Kosmoy). Downgrade ambitions: maintain for Kosmoy, stop category-creation marketing spend, decide pivot vs. sunset.
- VENDOR TRIPWIRE (continuous): Anthropic announces org-scoped cross-session/agent-teams messaging, or Claude Tag/session-sharing expands into per-person session-to-session messaging, BEFORE v1 ships. If pre-ship: reposition to cross-vendor/cross-org-only or stop. If post-ship: drop the same-org pitch, hold the moat quadrant only.
- MAINTAINER CAPACITY (rolling, first 6 months): unable to sustain at least monthly releases, or a security report goes unacknowledged beyond 72 hours. Either cut scope immediately or execute a deliberate, documented wind-down - for a consent product, a neglected security posture is worse than an archived repo.

## Judge panel

### bull — GO_WITH_CHANGES (72% confidence)

The honest case for building now rests on five pillars, each of which survives the worst evidence in the briefs rather than ignoring it.

1) The bad demand evidence is real but is the expected signature of a pre-articulation category, and the briefs contain the tell that distinguishes 'no need' from 'unarticulated need'. Yes: zero explicit public requests for cross-person AI Q&A, and the verifier's correction that askmesh.dev actually SHIPPED (62 npm versions since March 2026) with ~815 downloads is the single most sobering datapoint on the table — the exact hypothesis was tested and got near-zero adoption. But look at what askmesh lacks: no self-hosted relay, no zero-install remote-MCP path, no approval-as-product security story, no distribution effort (no launch found anywhere in the demand brief's exhaustive sweep). A tool nobody marketed getting no downloads is weak evidence against the category; it is strong evidence that shipping without positioning fails. Meanwhile the #28300 thread shows sophisticated users independently re-deriving askrelay's exact architecture — mailboxes, relays, Ed25519, bilateral approval — the moment they hit cross-boundary agent messaging. People re-derive it; they just haven't needed it across a person boundary yet at scale. That is what early MCP looked like too.

2) askrelay uniquely does not need external demand to reach its first validation gate. Kosmoy is a captive, real, daily-use first customer — the flagship-fit brief shows the modal solo-OSS killer is maintainer abandonment at ~6 months, and daily dogfooding pressure is the documented antidote. The demand question ('do pairs of humans exchange messages weekly?') gets answered with real usage data inside one company within weeks of v1, at near-zero marketing cost. Almost no pre-demand project gets a falsification loop that cheap.

3) The vendor clock argues FOR speed, not against building. The vendor brief's verified absence is strong: nobody ships, announces, or hints at person-to-person approval-gated session messaging; the credible 6–18-month threat is a same-vendor, same-org Claude Code mesh; the cross-vendor + cross-org + self-hosted + approval-as-product corner looks structurally unserved for 24+ months because no vendor has an incentive to build the other vendor's half or to make governance vendor-neutral. Vendor compression is an argument against a slow, gold-plated build — it is the argument for shipping the thin Go relay now, while the corner is empty. Add the answering-side moat the brief identified: shared org agents (Claude Tag, workspace agents) only see shared context; askrelay reaches B's live local session — uncommitted code, terminal state, private repos — which no channel bot can.

4) The downside is capped and the payoff structure is asymmetric. Market size clears the OSS bar even pessimistically (~100 real teams at 1% activation of the low serviceable estimate). The build is deliberately small: single Go binary + SQLite, design fully decided and adversarially verified. The flagship-fit brief is explicit that first-flagship failures die quietly — the modal outcome (dozens of stars, Kosmoy as only heavy user) still pays as a portfolio flagship demonstrating design rigor, which is the user's stated goal. The only reputational landmine is dismissive vulnerability response, which is behavioral and controllable.

5) The design already contains its own hedge. The futures brief's strongest finding: the approval-gateway adjacency (HumanLayer, gotoHuman, Cloudflare shipping HITL as a primitive) is askrelay's existing core — gates, revocable grants, signed envelopes, durable inbox carry over nearly intact, and it is precisely the layer a vendor's first-party messaging will NOT make vendor-neutral. If cross-person Q&A fails, the pivot is an extension ('approve an action' instead of 'approve a message'), not a rewrite. A bet where the primary hypothesis is cheap to test, the window is verified open, the first customer is captive, and the failure mode converts into the best-evidenced adjacency at near-zero cost is a bet worth taking now — with the changes below, because building it as originally framed (cross-person pitch only, docs-first pace) walks into every trap the evidence marks.

- Make same-owner cross-machine messaging ('your own agents across your machines') a documented day-one scenario: it is the only flavor with demonstrated demand (issue #28300 cluster, mcp_agent_mail ~2k stars) and askrelay's architecture serves it almost unchanged; cross-person becomes the differentiating superset.

### bear — NO_GO (60% confidence)

The case against askrelay is not that the design is bad — it is that every verified demand signal points away from the product's center, and the one natural experiment that tested its exact hypothesis already returned an answer.

1. Demand quality: this is builder-excitement, not pull — and the hypothesis is not untested, it failed its first public test. Across ~78k claude-code issues, HN's full-text archive, the OpenAI forum, and Reddit, the count of explicit requests for cross-person, approval-gated AI-session Q&A is zero. The demand that does exist (the #28300 cluster, mcp_agent_mail) is uniformly same-owner, and even it is weak: under 20 cumulative reactions across a year, and the flagship issue's thread is half self-promotion. Worse for askrelay: verification overturned the comforting 'nobody has tried it' framing. askmesh (@askmesh/mcp) is a functioning direct competitor — teammate-to-teammate agent Q&A over MCP with a daemon mode, 62 npm releases since March 2026 — with roughly 815 total downloads and a stalling release cadence. Someone shipped askrelay's exact pitch for four months and the market yawned. The #28300 users who independently re-derived mailboxes + Ed25519 + relays built them for themselves, not for colleagues; when they needed a colleague's context, the revealed-preference answer is that they Slacked the colleague. Category creation with zero expressed demand plus one visible failed attempt is the weakest possible demand posture.

2. The vendor clock strikes first exactly where askrelay's only real user lives. The moat claim — cross-vendor + cross-org + self-hosted + approval-as-the-product — is structurally genuine; I do not dispute that no vendor will build the neutral consent layer between Claude and ChatGPT across company boundaries. But that moat surrounds the quadrant with the LEAST demand evidence ('pilots and protocols, not purchase orders' for cross-org; zero expressed demand for cross-vendor). The quadrant with actual near-term usage — Kosmoy colleagues, all on Claude Code, same org — is precisely the quadrant the moat does not protect and the one vendor motion targets: Anthropic shipped agent-teams messaging primitives (Feb 2026), Claude Tag (June 2026), and first-party link-based session sharing with team members (a datapoint the demand brief missed entirely). The vendor-clock brief itself rates an org-scoped Claude Code session mesh 'plausible within 6–18 months.' So the launch plan is: validate in the exposed quadrant, survive on the unvalidated one. The moat and the demand are in different places, and a moat around an empty castle is a cost, not an asset.

3. Solo-maintainer base rates are brutal and askrelay wears the worst-case costume. 52% of audited MCP servers are dead; the median has 6 commits and one maintainer; reviewers now treat 'exactly one contributor' as dead-by-default. The cited counterexamples are non-transferable outliers (OpenClaw's author was already famous). The winners shipped weekly for months — this maintainer has a day job at the first customer. And category creation doubles the load: with no queue of users, the maintainer must simultaneously build, secure, document, AND manufacture the demand narrative. Kosmoy as captive first user has no documented adoption effect and creates a specific failure mode: an internal tool wearing an Apache-2.0 license, with usage metrics that never disconfirm because the first user is also the employer.

4. Security-burden asymmetry: when approval IS the product, the security bar is the product, and the cost-benefit is inverted. The evidence says security-positioned MCP projects get adversarially red-teamed within months (30+ MCP CVEs per 60 days; even Anthropic's reference server was hit), that a strong threat model does NOT convert to adoption by itself, and that only fast, competent incident response preserves trust. Translate that: askrelay must pay the full, permanent cost of a hardened design (spotlighting, quarantine, redaction, Ed25519, OAuth 2.1, ephemeral retention) and an indefinite solo incident-response SLA, receives zero demand credit for any of it, and suffers uniquely on-brand-damaging harm from the first slow patch — because a consent product with a consent bypass is dead in a way a convenience product with a bug is not. A vendor entering later carries none of this asymmetry. Guaranteed cost, speculative benefit, ruinous downside: that is the honest shape of this bet.

The strongest pro-side rebuttals — the approval-gateway hedge and 'it pays as a portfolio flagship even at modal outcome' — are real but concede my point: they are arguments for salvage value, not for demand. If the best case for GO is 'the failure mode is still a nice design document,' the market case has already lost.

The base-rate prediction is therefore concrete: askrelay ships, gets dozens of stars, Kosmoy is the only heavy user, a security researcher probes it within months, and the project faces the abandonment cliff at month 6-12. That is the median world and any go decision must pay in it. What genuinely moves askrelay off the base rate, upward: (1) it is product-shaped with a novel, explainable pitch, and the window's winners (Repomix, OpenClaw, FastMCP) were exactly product-shaped solo launches — generic servers supply the dead 52%, products supply the tail; (2) a captive daily-dogfooding first user is rare in this class and directly attacks the dominant failure mode, which is maintainer abandonment, not scandal; (3) the design rigor already on record (verified research, decision log, threat model as launch content) is well above class median for the security-scrutiny gauntlet that is guaranteed; (4) the approval-gateway adjacency means the modal-failure salvage value is unusually high — the core module is a hedge, not a dead end. Downward: solo-maintainer discount is now an explicit ecosystem heuristic, and the askmesh datapoint converts "unvalidated" into "tested once, no adoption yet." Net: the distribution is fat-tailed, the downside is quiet invisibility (reputationally cheap for a first flagship), the modal outcome still pays as a portfolio/design-rigor artifact plus a working internal tool for the employer, and the tail is career-making. Outside view says: proceed, but plan for the median, not the tail — and make the specific, evidence-backed moves that flip the dead-by-default signals.
